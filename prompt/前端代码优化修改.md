## 4.新增文章和后端白名单冲突

问题：不是，首先为什么有白名单，因为游客不需要登录即可看博客内容，但是不能增删改和点赞收藏，普通用户可以点赞收藏不能增删改，管理员可以增删改等任意功能，所以必须设置白名单，现在问题是新增文章接口是/articles这个路径是白名单里面的，我觉得只要前端改一下这个路径就行了，让后端使用Spring Security在controller方法上细粒度控制即可，我也不知道我说的是否对或者好，我们一起讨论

```
你的权限矩阵是对的，这是博客的标准模型：
     
  ┌────────────────┬─────────┬───────────┬────────────┐
  │      角色      │ 浏览/读 │ 点赞/收藏 │ 增删改文章 │
  ├────────────────┼─────────┼───────────┼────────────┤
  │ 游客（未登录） │ ✅      │ ❌        │ ❌         │
  ├────────────────┼─────────┼───────────┼────────────┤
  │ 普通用户       │ ✅      │ ✅        │ ❌         │
  ├────────────────┼─────────┼───────────┼────────────┤
  │ 管理员         │ ✅      │ ✅        │ ✅         │
  └────────────────┴─────────┴───────────┴────────────┘

  白名单的意义就是让"读"公开，这个方向完全正确。但**"改前端路径"这个方案有两个硬伤**，我们拆开看：

  为什么"改前端路径"不成立

  硬伤 1：改路径躲不开白名单。 你的白名单不是单个 /articles，而是通配符：

  - /articles
  - /articles/*

  /articles/* 匹配 /articles/ 下任意一段。你改成 POST /articles/add、/articles/create，URI 是 /articles/add，照样命中
  /articles/*，一样被白名单放行。除非你连通配符一起改，那本质还是改后端配置，跟改路径无关。

  硬伤 2：前端契约已经写死了，是 REST 风格。 你前端的 services/article.ts：

  createArticle → request.post('/articles')       // 新增
  updateArticle → request.put(`/articles/${id}`)  // 修改
  deleteArticle → request.delete(`/articles/${id}`) // 删除

  这是标准 REST，也是你已经定好的契约。改路径 = 改前端 service + 后端，两处都动。让后端迁就前端，别反过来。

  正确的方案：白名单按 HTTP 方法收窄（纯后端改动）

  问题的根源不是"路径在不在白名单"，而是**"白名单没区分方法"**——permitAll 把 POST 也一起放了。改成方法感知即可：

  ① 白名单只放行 GET（读），写操作自然落到 authenticated()：

  interceptor:
    whitelist:
      - /auth/login
      - /auth/me
      - GET:/articles
      - GET:/articles/*
      - GET:/categories
      - GET:/tags
      - GET:/archives
      - GET:/stats
      - /doc.html
      - /webjars/**
      ...

  ② SecurityConfig 解析方法前缀（原来是 antMatchers(pattern) 不带方法）：

  for (String item : securityProperties.getWhitelist()) {
      String[] parts = item.split(":", 2);
      if (parts.length == 2) {
          authz.antMatchers(HttpMethod.resolve(parts[0]), parts[1]).permitAll();
      } else {
          authz.antMatchers(item).permitAll();
      }
  }

  ③ JWT 过滤器始终解析 token（有 token 就解析，白名单不短路）——这样 @PreAuthorize 才有 Authentication 可判断。这个上一轮已经讲过了。

  改完之后的访问控制变成三层，正好兑现你的矩阵：

  ┌───────────────────────────┬──────────────────────────┬───────────────────────────────────┬────────────────────────────────┐
  │           请求            │          URL 层          │              方法层               │              效果              │
  ├───────────────────────────┼──────────────────────────┼───────────────────────────────────┼────────────────────────────────┤
  │ GET /articles             │ 白名单 permitAll         │ —                                 │ 游客✅                         │
  ├───────────────────────────┼──────────────────────────┼───────────────────────────────────┼────────────────────────────────┤
  │ POST /articles/{id}/like  │ 非白名单 → authenticated │ —                                 │ 登录即可（游客❌，普通用户✅） │
  ├───────────────────────────┼──────────────────────────┼───────────────────────────────────┼────────────────────────────────┤
  │ POST /articles（新增）    │ 非白名单 → authenticated │ @PreAuthorize("hasRole('ADMIN')") │ 仅管理员✅                     │
  ├───────────────────────────┼──────────────────────────┼───────────────────────────────────┼────────────────────────────────┤
  │ PUT/DELETE /articles/{id} │ 同上                     │ 同上                              │ 仅管理员✅                     │
  └───────────────────────────┴──────────────────────────┴───────────────────────────────────┴────────────────────────────────┘

  这样前端一行不用改，还是 POST /articles；白名单继续存在，管"游客能读哪些"；细粒度角色控制交给 @PreAuthorize，三层各管各的。
```

## 5.新增文章修改为上传图片

问题：文章管理为什么不使用上传图片框，然后由后端上传aliyun返回url

```
你说得对，这本来就应该用上传框。现在文章管理里"手填 URL + 插入假
  URL"不是刻意的设计决定，而是上传链路还没建起来时的过渡写法。证据在代码和提交时间线里：
     
  为什么现在是手填 URL

  1. 后端根本没有上传接口可调用。 AliyunOSSOperator 早就写好了（upload() 能返回完整 OSS URL），但一直没暴露成 POST /upload 的
     Controller。没有这个接口，前端上传框就算做了也传不上去。
  2. 前端 UI 是照着占位实现的。 MarkdownEditor.vue 的"图片"按钮（insertImage）插入的是写死的 https://example.com/图片.jpg；封面的"封面图
     URL"（ArticleEditPage.vue:134）就是个手填 el-input。这些明显是"先占个位"的实现。
  3. 时间线说明前后端还没对接完。 编辑器 md 图标是 08-27 加的（01a5774），而文章相关后端类（含空壳 Controller）到 09-01
     才出现（4c1a04b），昨天的事。也就是说文章管理界面是在后端接口就绪前、对着 mock/契约数据搭出来的，上传这种依赖后端的能力自然被留到了后面。

  所以结论是：当前是"后端 upload 未实现 → 前端只能先用 URL 占位"，不是故意不用上传框。 你现在提的正是该补上的最终形态。

  按你说的方案改造需要做的事

  后端（补上缺失的一环）
  - 新增 POST /upload：接收 multipart 文件 → 校验类型/大小 → AliyunOSSOperator.upload() → 返回 Result<{ url: string
    }>。需登录+管理员权限（不能放白名单）。

  前端
  - 封面：把 ArticleEditPage.vue 的 URL 输入框换成 el-upload，传图 → 返回 URL → 回填 form.cover（可保留一个"已填 URL"的输入框用于手工替换）。
  - 正文图片：MarkdownEditor 的图片按钮改成真正的"选文件 → 调 /upload → 把返回 URL 插成 ![](url)"，同时可在上传中显示 loading。

  改完后链路就是：上传框 → 后端传 OSS → 返回 URL → 存进 cover/content → 新增文章接口照常把 URL 存库 → 展示时 <img src> 直接出图。

  要我现在就把这三件事（后端 upload 接口 + 封面上传框 + 编辑器图片按钮）一起实现吗？
```
